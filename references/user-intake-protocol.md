# AI 用户接入与费用预演协议

每次在新工程或新会话启用本 Skill 时，AI 必须先执行本协议。目标是让使用者在付费生成前清楚知道要提供什么、预计调用多少次、可能得到多少合格动作以及最坏费用上限。

## 第一条回复必须包含

简要说明管线分成两个阶段：

1. 免费预演：检查人设图、设计动作、计算运动包络、规划分辨率和批次、估算费用、保存脱敏 dry-run。
2. 付费执行：仅在使用者确认方案和调用上限后提交视频任务；生成后用实际 usage 重算成本并完成提取、QA 和游戏预览。

向使用者索取以下信息。允许对非关键项提出默认值，但不得替使用者决定付费上限。

| 信息 | 使用者需要提供 | AI 可建议的默认值 |
|---|---|---|
| 服务 | Seedance 或其他视频服务、目标模型 | Seedance 2.0 Mini；执行时核对官方模型 ID |
| API 权限 | 只确认本机已配置环境变量，不索取密钥内容 | 火山方舟使用 `ARK_API_KEY` |
| 人设图 | 单人物、完整身体、最终服装/武器的附件或本地路径 | 横版角色默认朝右；背景与角色颜色分离 |
| 动作清单 | 动作名称、优先级、是否循环、移动/受力方向 | 独立动作 idle→动作→idle；行走 start→loop→end |
| 位移需求 | 跳跃、闪避、突进、击退等是否真实移动 | 保留真实 root path，不强制原地 |
| 素材规格 | 最终画布、人物高度、FPS、root/baseline、目标引擎 | 像素人物先比较 128 与原生 256；默认 nearest |
| 质量目标 | 更重视可读动作数量还是严格游戏可用率 | 同时报两种单位成本，不混为一谈 |
| 付费边界 | 最大调用次数、允许分辨率、是否允许付费重试 | 默认零自动付费重试；失败提交也占槽位 |

明确告诉使用者：不要在聊天、提示词、仓库或截图中粘贴 API Key。若环境变量未设置，AI 仍完成所有免费预演并停在提交之前。

## AI 必须补问的动作信息

对每个动作建立记录：

```text
name:
purpose:
loop: true/false
facing:
world travel:
incoming force:
expected complete duration:
start pose:
terminal pose:
root path:
weapon/hair/scarf maximum reach:
priority: required/optional
```

若使用者只说“攻击、跳跃、闪避”，AI 应先提出动作设计与示意帧，不直接写生成提示词。默认横版 2D 角色朝右；正面攻击与受击来自右侧；前进/前闪向右，后退/后闪向左但脸仍朝右。

## 费用预演需要知道的信息

执行时从官方文档确认：

- 模型 ID 与输入类型；
- 支持的分辨率、画幅、最低/可选时长和固定 FPS；
- 是否启用音频会改变价格；
- 当前每百万 tokens 或其他计费单价；
- usage 中用于结算的实际字段；
- 失败任务、取消和重试的计费规则。

从动作设计得到：

- 每个动作包含开始、动作、恢复后的完整占用时长；
- 人物、武器、root path 的 union 与 20–30% 大动作冗余；
- 每格所需源人物像素高度；
- 同屏主体数和每主体顺序动作数；
- 历史可读率与严格合格率；
- 使用者允许的任务数和重试数。

生成前输出至少两个候选方案，例如“480P 少主体”和“720P 低密度”，并使用：

```text
每主体时间容量 = floor(视频时长 / 完整动作占用时长)
请求动作数 = 安全主体格数 × 每主体时间容量 × 视频条数
预计合格动作数 = 请求动作数 × 历史严格验收率
预计任务成本 = 预计 tokens / 1,000,000 × 当前单价
预计单个合格动作成本 = 预计总成本 / 预计合格动作数
最坏授权成本 = 单任务上界 × 授权槽位数（包含允许的失败/重试）
```

面积或历史 tokens 只用于预估。生成后必须用最终响应的实际 usage 和提交时价格覆盖估算。

## 最高性价比批次规则

按以下顺序优化，而不是盲目提高分辨率或格子数：

1. 先一次性收集并设计全部动作，避免每个动作单独发现方向、尺度和端点规则。
2. 当最短视频长于单个完整动作时，在同一人物时间线上顺序安排多个不同动作，用 canonical idle 作为分隔；不要重复动作填时长，也不要把一个动作拉成慢动作。
3. 若完整动作约 2 秒、最低视频约 4 秒，则单人物理论上最多放两个动作；只有两段都保留可识别的开始和恢复时才计入产量。
4. 默认选择通过源像素和动作包络检查的最低分辨率。当前像素人物经验是优先 480P、少主体；同屏人物越少，动作逻辑、方向和身份越可控。
5. 只有当跳跃、闪避、突进、击退或长武器需要更大空间，或实测验收率证明能抵消成本时，才提高到 720P或降低格子密度。
6. 同屏多格先检查每格人物源像素和 padded motion envelope。格子越多不等于合格动作越多；密集布局必须按严格验收率折损预计产量。
7. 把动作按相近的空间包络和控制难度分组。小幅 idle/block/hit 可组合；大位移 jump/dodge/lunge 应分配更宽画布或更低密度。
8. 比较 `总成本 / 严格合格的不同动作`。同时报告每可读动作成本，但不能用“看得懂”冒充“可直接用于游戏”。
9. 失败提交、不可用动作和付费重试全部计入总成本。禁止只用成功样本美化单位成本。

## 付费提交前必须给使用者看的摘要

使用下列表格，不得只说“预计很便宜”：

| 方案 | 分辨率/时长 | 视频条数 | 同屏主体 | 每主体动作 | 请求动作 | 预计严格合格 | 预计总成本 | 最坏上限 | 主要风险 |
|---|---|---:|---:|---:|---:|---:|---:|---:|---|

随后列出：

- 每条视频的动作顺序与格子布局；
- 每个动作 storyboard 和所需画布；
- 采用/拒绝某分辨率的原因；
- 是否允许重试；
- 将要提交的模型、画幅、时长、音频/水印设置；
- 脱敏 dry-run 保存路径。

最后请求范围明确的授权，例如：

```text
请确认是否授权提交：480P 两条、每条 4 秒、无音频、零自动付费重试，预计 ¥X，最坏不超过 ¥Y。任何已提交失败任务也占用这两个槽位。
```

未获得明确授权时停止在 dry-run。使用者授权一次后，不得扩大模型、分辨率、时长、数量或重试范围。

## 生成后的强制汇报

逐条报告：task 状态、实际 tokens、实际人民币、视频哈希、可读动作、严格合格动作和失败原因。最终对每种质量给出：

```text
实际单个可读动作成本
实际单个严格合格动作成本
总失败/重试成本
缺失动作和 fallback
游戏预览路径
```

不要替使用者判断主观画质胜者。先让使用者在相同显示尺寸下试玩，再把其评价与实际成本合并比较。
