# 使用前准备

在编写提示词或提交任何付费任务前，与使用者逐项确认本页。缺少 API Key 时仍可完成动作设计、画布规划、成本预估和 dry-run，但不能提交生成。

## 必需输入

### 1. 服务和 API 权限

- 确认视频服务、区域、模型 ID 和账号可用配额。
- Seedance/火山方舟把密钥保存在本机环境变量 `ARK_API_KEY`。不要把真实值写入提示词、JSON、日志、截图、Git 或聊天消息。
- 在执行时重新核对官方模型参数、最低时长、可选分辨率和价格；这些信息会变化。
- 明确本轮付费上限：允许的任务数、分辨率、最长时长、是否允许付费重试。失败的已提交任务也按占用额度处理。

Windows 当前终端示例：

```powershell
$env:ARK_API_KEY = "在本机填写，不要提交到Git"
```

如果要长期保存，优先使用系统密钥管理或受控环境变量，不要在 Skill 文件夹创建明文密钥。

### 2. 人设图

已进入实际游戏资产阶段的角色，主参考必须是已经批准并实际运行的 canonical runtime 像素 Idle，而不是高分辨率原画。提交前记录其原生图片尺寸、canonical canvas、可见人物高度、root、baseline、朝向、调色板与采样方式；参考板默认原生像素 1:1 保留透明度。若 provider 必须放大，只能使用已声明的整数倍 Nearest，不得使用平滑重采样或生成式重绘。原画和转面图仅作为二级身份审计证据。

至少准备一张清晰角色参考：

- 单一完整角色，无遮挡、无文字、无第二个人物；
- 与目标动作相同的服装、发型、体型和武器；
- 2D 横版默认朝屏幕右侧；
- 尽量使用中性站姿、固定比例和清楚的脚底；
- 背景简单并与角色颜色分离。若目标是绿幕抠像，参考图也应使用经过检查的统一色键背景；角色本身含绿色时改用其他键色。

可选补充：正背面设定、武器尺寸、表情表、颜色表。多视图拼在一张图可能诱发重复人物，只在确有需要且已测试时使用。

### 3. 动作表

每个动作至少说明：

- 名称与用途；
- 是否循环；
- 默认朝向、移动方向、受力方向；
- 是否带真实 root displacement；
- 预期动作时长；
- 开始姿势和结束姿势；
- 武器/发丝/围巾等最大伸展范围。

默认独立动作使用 `canonical idle → anticipation → action → recovery → canonical idle`。行走等循环动作使用独立的 `start → loop → end`，不能循环整段 idle-to-idle 视频。

先用 `scripts/plan_action_storyboard.py` 生成示意帧与动作包络。没有示意帧、root path 或安全画布结论时，不提交付费生成。

### 4. 游戏素材规格

确认：

- 最终画布，如 128×128 或 256×256；
- 人物本体目标高度；
- canonical root 与脚底 baseline；
- art FPS 和游戏 logic FPS；
- 像素风、手绘或其他风格；
- 导入目标，如 Godot、Unity、自定义 Web runtime；
- 是否需要透明 PNG、固定调色板、描边、法线/光照或 root-motion 数据。

视频生成分辨率不是最终 Sprite 画布。先以足够的源像素生成，再抠像、注册、缩小和量化。

## 如何计算动作消耗

### 生成前

分别计算时间容量和空间容量，取更严格者：

```text
每主体时间容量 ≈ floor(视频时长 / 完整动作占用时长)
安全格子数 = 通过源像素预算和大动作包络检查的格子数
请求动作数 = 每主体时间容量 × 安全格子数 × 视频条数
预计合格动作数 = 请求动作数 × 历史验收率
预计单个合格动作成本 = 预计总任务成本 / 预计合格动作数
```

“完整动作占用时长”必须包含可识别的开始、动作和恢复，不要只用攻击活跃帧时长。短动作可以在一条最低时长视频内按顺序放多个不同动作，但不能用重复动作冒充产量。

使用：

```text
python scripts/plan_sequence_batch.py ...
python scripts/estimate_action_cost.py ...
```

源像素和动作包络不通过时，即使时间还能塞入更多动作，也必须减少格子或提高单格空间。默认优先少主体的 480P；只有真实位移、武器伸展或验收率证明需要时才升级 720P。

### 生成后

从服务最终响应的 `usage` 读取实际 tokens，并按任务提交当时的官方价格计算：

```text
任务人民币成本 = actual_total_tokens / 1,000,000 × 当时每百万 tokens 单价
单个可读动作成本 = 总成本 / 可读且完整的不同动作数
单个严格合格动作成本 = 总成本 / 通过身份、方向、idle端点、尺寸、root/baseline和连续性验收的动作数
```

实际 receipt 永远覆盖面积比例或历史 tokens 估计。失败任务、付费重试和不可用动作都要保留在总成本中。

## 交付前检查

- 保存脱敏 dry-run、task ID、最终响应、原视频哈希、usage 和价格依据。
- 原视频下载后再按 PTS 和运动能量识别真实动作边界。
- 给每种质量记录请求动作、可读动作、严格合格动作及各自单位成本。
- 保留原始素材与失败记录；不要用另一分辨率素材冒充缺失动作。
- 在实际游戏大小和真实运行时中长播验证，不只看 contact sheet。
